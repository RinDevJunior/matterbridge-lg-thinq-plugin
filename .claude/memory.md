## Architecture Insights

<!-- Patterns and relationships discovered during analysis -->

- V1 room-detection flip-flop root cause (confirmed Aug 3, 2026, real S8 log + floor-plan photo): `MapInfoListener.tryParseV1MapBinary` (`mapInfoListener.ts:211-238`) resolves+publishes a room from EVERY independent V1 map push with zero temporal smoothing (`onV1RoomResolved`→`AreaManagementService.setV1ResolvedSegment`, unconditional overwrite). Rc05's containment tiers (PR #154) are correct per-snapshot; the miss is one layer up. Floor plans where one room (e.g. a corridor) borders most others amplify this: `resolveCurrentRoom`'s tier-3 `findNearestSegment` (bounding-box center, not true centroid) flips between different neighbors on tiny pose noise near that hub. Fix: 2-consecutive-match confirmation gate added to `setV1ResolvedSegment` (`v1PendingResolution` map) — see `workspace/room-detection-flip-flop-investigation/plan.md`.
- Live map updates: `resolveInitialAreas` must sync-bootstrap via `fetchAndApplyMapInfo`/`fetchAndApplyRoomMap` (ignore V2); public `getMapInfo`/`getRoomMap` stay V2-only when `liveMapUpdates`. `handleActiveMapChanged` must intersect with Matter `supportedAreas` before writing `selectedAreas`.
- Multi-map areas: partial room-map fetch/push merges by `mapId` via `mergeSupportedAreasByMap` (keeps other maps, re-indexes areaIds); full `mapInfo.allRooms` / V1 map-info push stays full replace.
- Multi-map + `enableMultipleMap`: ON → bootstrap all physical maps via `switchMap`+sync fetch, merge by mapId; OFF → primary only (`maps[0]`) via `getSupportedAreas(..., false)` — wired from `configManager.isMultipleMapEnabled`.
- No code path calls V1 `dispatcher.getHomeMap` (`get_map_v1`) on a recurring basis — `PollingService` only calls `getDeviceStatus`; `AreaManagementService.startPeriodicRefresh` only calls `getMapInfo` (`get_multi_maps_list`). A V1 position-based fallback needs its own explicit trigger.
- `MapInfoListener.tryParseB01MapBinary` skips `Protocol.map_response` when `deviceProtocol === ProtocolVersion.V1` (`mapInfoListener.ts:165`), but a SEPARATE `tryParseV1MapBinary` (`:211-238`) handles V1 map binaries via `decryptAndUnzipV1Map`→`resolveCurrentRoom`→`onV1RoomResolved`; confirmed firing correctly in real S8 logs (Jul 25, corrects a prior stale claim that V1 binaries were dropped entirely).
- `OperationStatusCode.WashingTheMop`(23) override (`stateResolver.ts:128-139`) writes `operationalState=FillingWaterTank` for ~2-3min at clean-start (real mop-pad wash phase) before `Running` — Apple Home master tile likely shows this as "Preparing" (unconfirmed, HomeKit-side); `RvcRunMode.currentMode`/`RvcCleanMode.currentMode` update correctly/promptly throughout, independent clusters.
- V1 `mapParser.ts` `resolveCurrentRoom`: exact-pixel-match tier only matches pixels where `parseImageBlock` recorded a segment — misses on wall/obstacle/type-0 pixels, common at room boundaries. Fallback tiers: (1) bounding-box containment check (single-match-only, Jul 28 merged), (2) nearest-centroid distance. **Jul 28:** `LegacySegmentInfo` now carries `boundingBox` (raw pixel-space); `findContainingSegment` private method inserted in `resolveCurrentRoom` between exact-pixel and `findNearestSegment`, returns single segment only (0 or 2+ → falls through to centroid). No shared point-in-rect helper (`legacyIslandDetection.ts` only has rect-rect `boxesOverlap`).
- V1 `"rr"`-frame block types beyond this repo's known 4 (charger=1, image=2, robot=8, cleaned=11): `FORBIDDEN_ZONES=9` (no-go zone), `VIRTUAL_WALLS=10`, `NO_MOP_ZONE=12` — same buffer, same `get_map_v1` RPC, no new RPC needed (corroborated byte-for-byte by ioBroker.roborock + roborock-gitlab, independent authors). Wall payload = 2 (x,y) endpoints/8 bytes; zone payload (9 and 12 share one decoder) = 4 corners/16 bytes; count field is `u32` at block offset `+0x08`, entries start at `dataPosition+hlength`. Coordinate units inferred as raw mm (same space as robotPosition), medium confidence only — no real captured buffer with these blocks populated exists anywhere checked (this repo or the 2 corroborating OSS repos). See `workspace/virtual-wall-detection-feasibility/answers-virtual-wall.md`.

- Greenfield repo confirmed Sep 8, 2026: `matterbridge-lg-thinq-plugin` had no `src/`/`package.json` at task start — `wiki/reference-workspaces.md` created this cycle (4 rows: matterbridge-example-dynamic-platform, homebridge-lg-thinq, homebridge-webos-tv, matterbridge-roborock-vacuum-plugin) for future investigator/wiki-manager lookups.

## Known Patterns

<!-- Coding patterns established in this project -->

- **Commit messages:** `<type>: <short summary>` + optional why-body, per `.claude/templates/commit-message.md` (PRs: `pull-request.md`). Imperative mood; no scope; no `Co-Authored-By`.
- New config sections in schema use JSON Schema `if/then` blocks under `advancedFeature.allOf`.
- **Agent frontmatter:** `effort`/`maxTurns` after `color`, before `tools`; `tools` MUST be a comma-separated string — YAML block lists silently fail and the subagent falls back to Read/Write/Edit/Bash only.
- **Subagent toolsets (macOS, re-verified Jul 10 2026):** native `Glob`/`Grep` absent from Task subagents — `mcp__glob-grep__*` is the only working search. `LSP` newly reachable in wildcard-tools subagents via deferred ToolSearch (one probe; explicit `tools:` lists historically never got it) — don't rely on it in agent definitions.
- **Subagent task tracking:** `TaskCreate`/`TaskUpdate`/`TodoWrite` never reach Task subagents (verified Jul 10 2026, direct-executor probe) — never list them in agent frontmatter; EM tracks pipeline steps in the main session, subagents report plain text (use a `progress.md` file in the task folder if live status is ever needed).
- **ThinQ Connect (PAT, Oct 21, 2026):** `src/services/thinqConnect/` is separate from EMP `services/thinq/`; `ThinqConnectApiError` (`THINQ_CONNECT_ERROR`) carries `resultCode` in metadata. Axios errors map via `axios.isAxiosError`.
- **`format:ci` rewrites files in place** (reports `FORMAT: N file(s)`); re-run `format:ci` until `FORMAT PASS` before lint/type-check.
- **ThinQ command body (Oct 22, 2026):** `sendCommand*` spreads the payload AFTER `command:'Set'` — an explicit `command: undefined` wipes the default; omit the key instead.
- **Never `git mv` (Oct 23, 2026):** it stages; move files with plain write/delete (`git restore --staged` to undo).
- **Env pitfall (Oct 21, 2026):** `node_modules/matterbridge` can be an EMPTY dir → `type-check:ci` fails with TS2307/TS2339 cascade on every file. Not a code error; check `ls node_modules/matterbridge` before blaming code, and leave the reinstall to compiler.

## Decisions Made

<!-- Architectural and design decisions with rationale -->

- LG ThinQ+webOS migration (Sep 8, 2026): two device families, one platform. `services/thinq/`+`platform/thinq/` (cloud EMP) and `services/webos/`+`platform/webos/` (local SSAP websocket) share only `module.ts` and one namespaced `node-persist` instance. Phases: 1=ThinQ AC, 2=rest of ThinQ, 3=webOS, 4=MQTT (deferred), 5=ThinQ1 legacy (deferred). See `workspace/migrate-lg-thinq-to-matterbridge/plan.md`.
- `MatterbridgeServiceAreaServer.selectAreas` (`@matterbridge/core`) runs our handler, then calls `super.selectAreas` with the ORIGINAL request and writes `selectedAreas` directly. Empty-input resolution must go in `RoborockServiceAreaServer.selectAreas`, forwarding a RESOLVED request to super; an `updateAttribute` from the command handler always loses the race.
- Active map: `homeInFo.activeMapId` inits `-1` (`deviceConfigurator.ts:105`), written only by B01/Q7 `onActiveMapChanged`, so V10/V1 never update it (`RoomIndexMap.getAreaId` misses) → use `getAreaIdV2(roomId)`. No Matter "current map" attribute exists. SELECT_AREAS empty-list fallback: Matter `selectedAreas` mapId → `activeMapId` (if not -1) → first `supportedAreas` mapId.
- ThinQ AC capability gating: `AirConditioner` ctor (`@matterbridge/core/dist/devices/airConditioner.js`) always builds full Thermostat+FanControl and cannot be narrowed. `Behaviors.require()` THROWS on a 2nd call per cluster id, so reduced-feature devices hand-compose via `MatterbridgeEndpoint` `create*ClusterServer` before any `require()` (pattern: `matterbridge-example-dynamic-platform/src/module.ts:1920-1980,2100-2230`).
- ThinQ AC energy layout (Sep 20, 2026): when `supportsEnergyMonitoring`, the AC endpoint itself has [roomAirConditioner, powerSource, electricalSensor] + PowerTopology + ElectricalPowerMeasurement; no `EnergyMonitor` child. Required for Apple Home's Energy tab and per-device detail with a bridged AC (live iOS 27 tests).
- ThinQ Connect (PAT), Oct 21, 2026: `src/thinqConnect/` (platform) + `src/services/thinqConnect/` (API client/pure helpers), self-contained (no V1/`PlatformConfigManager`/`cli/` imports); neutral helpers in `services/thinqConnect/thinqConnectWasher.ts`; only `module.ts` imports both. Never `await updateAttribute` inside a command handler (deadlock) → use `deferThinqConnectApply`.
- ThinQ Connect washer start/stop (Oct 21, 2026): refusal MUST throw (no state mutation); STOP not POWER_OFF; no auto POWER_ON; handlers always registered (no opt-in). matterbridge 3.11.x (Oct 27 correction, supersedes the 3.10.9 "fire-and-forget" view) AWAITS `executeHandler` before mutating and returns on the FIRST matching handler, so a throw blocks the mutation (no revert needed).
- Matter server-mode identity (Oct 22, 2026, matterbridge 3.11.0): node store key = `deviceName.replace(/[ .]/g,'')` (`matterbridge.js:2171`); stored serial/uniqueId WIN over new ones (`:1920`); child endpoints keyed by endpoint `id`, so a new id = a new endpoint number.
- V1 washer vt-course body (Oct 27, 2026): `course` + all four option cells (LG app shape). Rinse 1:1 None→NO_RINSE / Normal→RINSE_2 / Extra→RINSE_3 / Max→RINSE_4 (RINSE_1/5 display-only). RINSE_3/4 allowed by every course with a rinse list; TURBO39/SPEED14/RINSE_SPIN lack NO_RINSE. Guard: `checkWasherVtGuard('vt-course')` + in-flight lock + 10 s cap, no retry, never `wmControl`.
- V1 washer vtCtrl runtime (Oct 23/29, 2026): pure logic in `platform/thinq/thinqWasherVtCtrl.ts` (CLI = re-export shim); `WasherVtController` = fresh read, guard, 10 s timeout, poll, in-flight lock, 2 min Start lock-out. Start tap 1 stages course (Remote Control OFF), tap 2 sends START. Ack code is NOT proof: confirm refused values via post-send read (`SendResult.afterFields`). Option A (omit course cell) ships behind `WASHER_VT_OMIT_COURSE_CELL_DEFAULT`. See `workspace/washer-vtctrl-carry-forward/plan.md`.

## Test Patterns

<!-- Test conventions and gotchas -->

- **Deferred-write handler tests (Oct 22, 2026):** after `await handler()` call `vi.advanceTimersByTimeAsync(THINQ_CONNECT_DEFERRED_APPLY_DELAY_MS)` before asserting writes; `vi.clearAllMocks` does NOT reset `mockImplementation`/`mockRejectedValueOnce` — `mockReset` in afterEach for never-resolving writes.
- **Washer vtCtrl learning tests (Oct 29, 2026):** a learned refusal needs a post-send read showing the value NOT applied; `createHarness` steps are index-based (last repeats), so `setSteps` resets the read cursor. `mockResolvedValueOnce` the ack only for the send under test.
- **`.claude/tools/*.cjs` unit tests (Oct 21, 2026):** vitest include is `src/**/*.test.ts` only, so test lives in `src/tests/tools/`, loads the `.cjs` via `createRequire(import.meta.url)` + `asCliRunner(value: unknown)` cast (no `as unknown as`). Works because the tool guards its stdio server with `require.main === module`.
- **Washer Matter display tests (Oct 24, 2026):** fake endpoint `asPartial<MatterbridgeEndpoint>({updateAttribute: vi.fn()})`; assert write order via `mock.calls.map(c => c[1])`. `createFakeWasherModel()` = valid 2-course plan. Option-returning builders: wrap in a throwing helper, never `!`/`?.` on the result.
- **Injected-clock trackers (Oct 24, 2026):** pass `new WasherCycleTracker(clock.now)` with a local `createFakeClock()`; no `vi.useFakeTimers`. Map-backed lookups (`ReadonlyMap`) make `'constructor'`/`'toString'` inputs safe.
- **ThinQ Connect test patterns (Oct 21, 2026):** endpoint mock via `vi.hoisted` object + `vi.mock('matterbridge/devices')` with `vi.fn(function(){return mocks.endpoint})`; polling via fake timers + `vi.getTimerCount()`. Assert outcomes with `toMatchObject({reason: expect.stringContaining(...)})`, never `if` (no-expect-in-conditionals). Bare `obj.prop;` statements fail lint (`no-unused-expressions`).
- **Washer command handler extraction (Sep 22, 2026):** pull handlers from `vi.mocked(mockEndpoint.addCommandHandler).mock.calls` with `(call: any[])` on `.find()`/`.filter()` callbacks (no TS7006); no `![1]`: use `stopCall?.[1] as () => Promise<void>`. For CLI arg expansion, test no-flag and with-flag paths separately.
- **Washer start-command payload tests (Sep 25, 2026):** configurator-level tests with a mocked `thinqWasherStartCommandResolver` must assert CALL ARGUMENTS (`toHaveBeenCalledWith` + `objectContaining` on `parameterOverrides`), never hardcoded mock returns (tautological). Override-precedence merge is tested directly on `extractWasherStartCommand()`.
- **ThinQ Connect AC test patterns (Oct 21, 2026):** mock typing: `vi.fn<Service['method']>()` + `Mock<Service['method']>`; `ReturnType<typeof vi.fn>` fails `Pick<Service>` assignability (TS2345). Shared PAT-free fixtures: `src/tests/helpers/thinqConnectAirConditionerFixtures.ts`; fire-and-forget `subscribeAttribute` handlers asserted via `vi.waitFor`.
- **Known source bug guard (Oct 23, 2026):** `it.fails` keeps the gate green while documenting a confirmed bug and flips red once fixed (then drop the marker). Live case: `extractWasherVtReturnCodes` skips nested `vtAck.response.*` shapes.

## Common Pitfalls

<!-- Things to avoid — bugs found, anti-patterns, footguns -->

- `DockStationStatus.isUpdownWaterReady` (bits 0-1 of dss) is parsed/observable but EXCLUDED from `hasError()`/`getMatterOperationalError()` (Jul 22, 2026 fix, `rvc-unable-to-complete-cleaning-error`). Real hardware shows it=1 (Error) as steady-state idle/charging, not transient fault — unreliable error signal, unlike the 5 other dss fields.
- AC keep-alive gap confirmed real (Sep 17, 2026): reference's `temperatureKeepAliveCommandForDevice` (`AirConditioner.ts:644-661`) POSTs `service/devices/{id}/control` w/ `ctrlKey:'allEventEnable'`, `dataKey:'airState.mon.timeout'=70`, every 60s — DIFFERENT call than the GET-based poll (`platformMonitor.ts:104-123` runs both concurrently, proving non-redundancy). This repo's poll (`thinqDeviceService.ts` `getListDevices`, GET only) does NOT cover it — zero hits for `allEventEnable`/`mon.timeout` in `src/` pre-fix. See `workspace/ac-keepalive-heartbeat/plan.md`.
- `refreshIntervalSeconds` default mismatch (Sep 17, 2026): `platformConfigManager.ts:16` code fallback = 5s, but `schema.json`/`config.json` advertise `default:60`. Only bites if the field is truly absent from saved config (not a normal-UI-path issue) — flagged, not fixed.
- ThinQ MQTT message shape confirmed identical to REST snapshot shape: `{ deviceId, data: { state: { reported: {...} } } }`, and `reported` is the same flat `airState.*`-keyed bag `ThinqSnapshot`'s constructor already accepts — zero new mapping logic needed, both polling and MQTT feed the exact same `ThinqDeviceUpdateListener` callback.
- `npm install` (plain, no args) SILENTLY REMOVES a prior `npm link matterbridge` symlink from `node_modules/matterbridge` (matterbridge isn't a `package.json` dependency, only linked) — any implementer adding a new npm dependency mid-task must `npm link matterbridge` again afterward, or `type-check:ci`/`tsc` floods with `Cannot find module 'matterbridge'` across the whole repo (false-looking whole-codebase break, actually just the missing link).
- There is no `onOffOutlet` export in installed matterbridge 3.10.9/`@matterbridge/core` — the 0x010a/`MA-onoffpluginunit` device type's real exported symbol is `onOffPlugInUnit` (`matterbridgeDeviceTypes.js:272`, requires Identify+Groups+ScenesManagement+OnOff). Use that name, not `onOffOutlet`.
- `matterbridge-lg-thinq-plugin.schema.json`'s real validator is `@rjsf/validator-ajv8`+`ajv`8.20.0 (bundled in Matterbridge frontend, NOT this repo's dev-only `ajv`6.15.0 — check `references/matterbridge/apps/frontend/node_modules/`) with `allErrors:true,verbose:true`. Any leaf failure nested under 3+ if/then levels (e.g. `loginType`×deviceType×capability-gated) surfaces as generic `"must match 'then'/'else' schema"` PER ancestor node, not the real leaf error — cryptic but not a schema bug; find the real cause by compiling the schema with that exact ajv8 config against a constructed instance.
- V1 washer vtCtrl carry-forward (Oct 29, 2026, 2 live captures): firmware refuses `temp=TEMP_COLD` (returnCode 15) though the model lists it `selectable`, and with a `course` cell present it then applies the course default (COLD->40); `isWasherVtCourseApplied` over ALL sent cells turns that into `unconfirmed` -> `thinqWasherVtSelectionHandlers` reverts the user's real change in Home.
- Option-cells-without-`course` is a reachable LG-app builder branch but UNPROVEN on hardware, and the CLI cannot send it (`buildWasherVtRequest` returns `undefined` for `vt-course` with no course) — a `--no-course` CLI flag is a prerequisite for that live test. `extractWasherVtReturnCodes` DOES handle nested `vtAck.response.UNDEFINE` (the older `it.fails` note is stale).
- RJSF `ArrayField`: setting any `"ui:widget"` directly on an array field (not `items`) makes `isCustomWidget()` true → renders ONE widget for the whole array (`ArrayAsCustomWidget`, `value`=full array) instead of N per-item rows. `"ui:widget":"select"` needs `ui:options.enumOptions` (static, can't hold runtime-dynamic values — renders empty); `"ui:widget":"textarea"` works for any dynamic array (DOM coerces via comma-join) — use for "read-only array, one compact box" instead of a literal dropdown.

## Module Notes

<!-- Notes about specific modules, non-obvious behaviors -->

- Matterbridge/Matter API (Oct 24, 2026 rule): read `/Volumes/ExternalSSD/code/references/matterbridge`, never `node_modules/matterbridge`/`@matter`; CodeGraph first: `codegraph explore -p <that path> "<query>"`.

- `roomNameNormalizer.ts` (b01): pure module, no imports. `normalizeB01RoomName(roomName, roomTypeId?, roomId?)` returns non-empty; callers may still chain `|| fallback`. `rr_other` (typeId 0) always resolves to `Room ${roomId}`.

- Q10 map format: python-roborock's `lz4_block_decompress` (`b01_q10_map_parser.py:190-237`) is a hand-rolled zero-dep LZ4 _block_-format decoder, NOT a call into the Python `lz4` package — no size param, decodes until input exhausted.
- ioBroker's Q10 parser lives at `ioBroker.roborock/src/lib/map/q10/Q10YxMapParser.ts` (not `b01/`) — a structurally different "YxMap" format (28-byte header, version/pixLen/pixLzLen fields) vs python-roborock's `01 01`+offset-27/29 layout; only LZ4-block-format + big-endian u16 width/height are cross-corroborated.
- Q10 fix landed: `b01MapParser.ts.parseRoomsFromEncryptedBinary` routes `0x01 0x01`-prefixed payloads to new `b01Q10MapParser.ts`/`lz4BlockDecompressor.ts` (hand-rolled, zero-dep); Q7 AES+zlib pipeline untouched. `0x02 0x01` trace packets now route to `b01Q10TraceParser.ts` (`parseQ10TracePacket` → `B01MapInfo.currentPose` = last point; rooms/mapId/roomMatrix always empty/undefined) instead of falling through to the Q7 path — superseded a same-day minimal "recognize+skip, no parse" fallback that had landed on `dev` first.
- LG ThinQ washer snapshot shape (Sep 22, 2026, cross-checked homebridge-lg-thinq + ioBroker.lg-thinq): raw key prefix `washerDryer.*` for deviceType 201/221/222, but `washer.*` (remapped) for 223. Fields confirmed read: `state` (raw string enum: POWEROFF/POWERFAIL/RUNNING/PAUSE/ERROR/END/etc, NOT model-resolved), `remainTimeHour`/`remainTimeMinute` (zeroed when not running), `doorLock`/`remoteStart` (DeviceModel-lookup enums), `TCLCount` (maintenance counter). No course/cycle/spin-speed/water-temp fields read by either reference. `homebridge-lg-thinq`'s washer is 100% read-only (zero `deviceControl()` calls); `ioBroker.lg-thinq` DOES send washer commands (course download/start/stop via a heavy model-JSON-driven `dataSetList` builder, `lib/helper.js:1316-1405`) but has no TS precedent and no local sample model JSON to verify against. See `workspace/washer-integration/answers-washer-reference.md`.
- `0x02 0x01` confirmed = python-roborock `Q10TracePacket` (10-byte header + repeating i16be x/y pairs, robot_position=last point); NOT corroborated by ioBroker (different wire format, no `02 01` marker at all). Real-hardware repro: 598B during active cleaning vs 7076B full map. Live-validated on real Q10 S5+: real changing (x,y) coordinates, zero crashes across 8 invocations. `mapInfoListener.ts`/`roomMatrixResolver.ts` needed zero changes (already consume `currentPose` generically); area/room wiring stays out of scope.

- `FanControl` cluster (Matter model, `@matter/model/src/standard/elements/fan-control.element.ts:33-67`): `PercentSetting`/`PercentCurrent` are conformance `"M"` (mandatory, unconditional) — NOT gated by any Feature bit. Only SpeedMax/Setting/Current (MultiSpeed), Rock*(Rocking), Wind*(Wind), AirflowDirection(AirflowDirection), and the `Step` command itself (Step feature) are feature-conditional.
- `createOnOffFanControlClusterServer` (zero Feature flags) still fires `subscribeAttribute(FanControl,'percentSetting',...)` normally — matter.js has no protocol-level rejection for feature-less fan writes; caller must self-guard. Proven both by conformance model and live example (`matterbridge-example-dynamic-platform/src/module.ts:2163-2196`, `fanOnHigh`). `FanModeSequence` enum has exactly 6 members (0-5): OffLowMedHigh, OffLowHigh, OffLowMedHighAuto, OffLowHighAuto, OffHighAuto, OffHigh.
- `matterbridge-example-dynamic-platform/src/module.ts:1920-1980,2100-2230` has a full reduced-feature demo block: heating-only/cooling-only thermostats + 4 fan tiers (default/base/on-off/complete), each a manual `MatterbridgeEndpoint([fan,...])` composition with its own subscribeAttribute clamp/guard — reusable pattern for per-device Matter feature gating.
